# 번역 지연 원인과 전후 측정

2026-10-19, 현재 M3 Max·36GiB Mac. 모델은 TranslateGemma 12B Q4_K_M 그대로다. 프롬프트·생성 설정·번역문 캐시를 바꾸지 않았다.

## 원인과 변경

모델이 내려간 상태의 요청은 약 3.5–5.0초였으며 모델 로딩이 약 2.4–3.9초를 차지했다. 기존 Ollama의 최대 상주 모델이 1개라 요약 모델을 사용하면 번역 모델을 다시 올려야 했다. 매 요청의 모델 목록·정보 검사는 합계 약 3ms여서 유지했다. 앱에 의도적인 번역 지연은 없었다.

- `server/start-ai.sh`: 최대 상주 허용 1→2. `SPEECHBRIDGE_LOADED_MODELS=1`로 낮출 수 있다. 추론 병렬 수는 1 유지.
- 번역 `keep_alive`: 30분→`-1`. 요약은 30분. 메모리 압박·스케줄링에 의한 퇴거까지 막는 보장은 아니다.
- API 시작 시 실제 사용자 텍스트 없이 번역 모델 preload. 준비 실패 시 회원·저장 서비스는 시작하고 실패를 기록한다.

공식 동작은 [Ollama 모델 준비·유지 문서](https://docs.ollama.com/faq)에 따른다.

## 전후 결과

| 조건 | 표본 / 전후 각각 | 이전 | 이후 | 해석 |
|---|---:|---:|---:|---|
| 요약 모델 로드 뒤 번역, 평균 | 3 | 4.425초 | 1.980초 | 이 시나리오에서 55.3% 감소 |
| 준비된 번역, 평균 | 100 | 1.657초 | 1.665초 | 사실상 변화 없음 |
| 준비된 번역, p50 | 100 | 1.201초 | 1.172초 | 작은 차이를 일반 속도 향상으로 주장하지 않음 |
| 준비된 번역, p95 / p99 | 100 | 2.593 / 2.753초 | 2.578 / 2.639초 | 입력 길이별 차이 포함 |
| runner unload 후, 평균 | 3 | 4.185초 | 3.681초 | 작은 표본·순서·캐시 영향, 엔진 개선으로 해석하지 않음 |

개선 후 요약 전환 직후의 개별 시간은 **3.689 / 1.149 / 1.102초**다. 첫 전환에서는 여전히 번역 모델이 내려가 재로딩했고, 뒤의 두 번은 두 모델이 함께 남았다. 첫 전환까지 항상 1초라는 뜻이 아니다.

시작 시 preload를 별도 실행한 첫 요청 3회는 0.986 / 1.108 / 1.080초였다. 준비 자체에 1.960 / 1.625 / 1.618초가 들었다. 로딩 비용을 없애지 않고 시작 단계로 옮긴 것이다.

동일 입력 106쌍의 번역문은 106쌍 모두 같았다. 동일 출력 확인이지 정확도 보장은 아니다. 10개 동시 요청은 전후 모두 4개 성공·6개 429였으며, 거절 응답을 성공 응답 속도에 섞지 않았다. 큐·한 번에 하나인 추론·운영 rate limit은 그대로다.

## 측정 범위와 비용

12개 합성 문장을 100번 반복했다. loopback HTTP 개발 인증 경로의 완료 응답을 측정하며 `/api/tags`, `/api/show`, 추론 응답과 Ollama load/prompt/eval 시간을 분리했다. 반복 측정을 위해 **시험용 서버에서만** admission 시계를 전진시켰다. 실제 서비스 제한은 바꾸지 않았다. cold는 runner unload이며 OS 디스크 캐시 초기화가 아니다. 전환 시험은 요약 모델 로드 비용을 번역 시간에 포함하지 않는다. 앱 화면·STT·TTS·실기기 네트워크 지연은 제외한다.

추가로 실제 회원 HTTPS 서버에서 합성 대화 정리(5.455초) 뒤 번역 3회가 1.026 / 0.635 / 0.634초로 완료됐다. 이는 소수 smoke test이며 UI·마이크 체감 시간과 다르다.

두 모델이 함께 남았을 때 `/api/ps`의 `size_vram` 합계는 약 **14.6GiB**였다. 이 값은 전체 서버 RSS나 시스템 메모리 사용량이 아니다. 번역 전용 때보다 상주 메모리를 더 쓰는 선택이며, 다른 앱/음성 모델과의 메모리 압박 및 장시간 다중 사용자 부하는 추가 관찰이 필요하다.
