# 계정 삭제 구현과 남은 연결

2026-10-19 갱신. 서버 API·PostgreSQL 삭제/복원 보호와 앱 삭제 확인·기기 대기함 정리를 구현했다. 웹 삭제 경로·30일 백업 보존 정책·명시적 복원 활성화 도구까지 구현했다. 공개 운영 URL·운영자 정보와 실기기 검증은 별도다. 시연 계정은 삭제하지 않았다.

## 공식 배포 요구 확인

Apple은 계정 생성 기능이 있는 앱에서 계정 삭제를 시작할 수 있어야 하며, 계정과 관련 데이터를 삭제하는 흐름을 요구한다. 비밀번호 등 재확인 단계는 허용한다. [Apple 계정 삭제 안내](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)

Google Play는 앱 안의 삭제 경로와 앱 밖에서 삭제 요청을 시작할 수 있는 웹 경로를 요구한다. 현재 프로젝트에는 외부 공개 HTTPS 주소가 없으므로, 웹 구현과 실제 게시 주소 확보를 구분한다. [Google Play 계정 삭제 요구](https://support.google.com/googleplay/android-developer/answer/13327111?hl=ko)

## 구현된 계약

`POST /auth/delete`는 회원 Bearer 세션과 JSON의 `username`, `password`, `confirm: true`를 요구한다. 로그인한 계정의 아이디가 일치해야 하며, 현재 비밀번호를 다시 확인한다. 인증 경로의 요청 크기·시도 횟수 제한을 적용한다. 단순 로그아웃이나 요청 본문의 다른 사용자 ID로 삭제할 수 없다.

사용자 행 잠금과 트랜잭션 안에서 비밀번호·현재 세션 만료/폐기를 재확인하고, 복원 방지 영수증을 남긴 다음 사용자 행과 외래 키로 연결된 데이터를 삭제한다. 모든 세션이 함께 폐기된다. 응답을 잃은 경우 원래 삭제 요청의 토큰 해시와 아이디 해시로 성공 여부를 재확인하므로, 같은 아이디로 새로 만든 계정을 지우지 않는다. 삭제와 동시에 시작했던 로그인은 계정 행을 다시 확인하여 새 세션을 발급하지 못한다.

마이그레이션007의 `account_deletions`는 사용자 ID·아이디·삭제 요청 토큰의 SHA-256과 삭제 시각만 보관한다. 원문·비밀번호·원시 토큰을 저장하지 않는다. 일반 데이터 역할은 접근할 수 없고, 인증 역할도 이 영수증을 수정·삭제할 수 없다. 해시도 삭제 처리 목적의 기록이므로 `/privacy`에서 보관 목적을 안내한다. 삭제 영수증은 오래된 보존본을 통한 부활을 막기 위해 현재 자동 만료시키지 않는다.

마이그레이션008은 삭제 당시 남아 있던 모든 세션의 해시를 별도 영수증으로 보관한다. 해당 토큰의 후속 요청은 일반 만료와 다른 `account_deleted`를 반환한다. 이미 정리되어 DB에 없던 오래된 세션까지 삭제 상태를 확인할 수 있는 것은 아니다. 확인 근거가 없는 일반 인증 만료에서는 기기 대기 데이터를 지우지 않는다.

## 앱의 삭제·복구

설정의 `계정 삭제`에서 삭제 범위와 백업 보존 사실을 안내하고 현재 비밀번호를 다시 입력받는다. 요청 전에 암호화 인증 저장소에 REQUESTED를 저장하고, 응답을 잃으면 계정 사용을 차단한 채 결과를 재확인한다. 확인 중 `/auth/me`가 성공했다는 이유만으로 삭제 요청을 취소된 것으로 간주하지 않는다.

서버의 삭제 성공을 확인하면 CONFIRMED 상태를 저장한다. 앱은 녹음·AI·동기화 작업을 중단하고 이미 받은 입력의 저장을 마친 다음, 해당 origin/계정의 대기함만 지운다. 그 뒤 로그인 정보를 비운다. 저장소 잠김·쓰기 실패 때는 삭제 확인 상태를 유지하고 재시작 또는 `정리 재시도`로 이어간다. 다른 계정 대기함과 명시적으로 가져오지 않은 기존 기기 기록은 건드리지 않는다.

## 웹 삭제

`GET /account/delete`에서 로그인 → 삭제 범위 확인 → 비밀번호 재입력·명시적 동의 → 삭제를 진행한다. 토큰은 페이지 메모리에만 두며 브라우저 저장소/쿠키에 저장하지 않는다. 취소하면 세션을 폐기한다. CSP, no-store, 프레임 삽입 금지, 외부 사이트의 POST 차단을 적용했다. `/privacy`는 수집 내용·음성 임시 처리·보존 범위를 설명한다.

실제 브라우저에서 시연 계정 로그인·확인 화면·취소·개인정보 안내를 검사했다. 이 계정의 영구 삭제는 하지 않았다. HTTP 삭제 성공과 데이터 격리는 별도 테스트 DB에서 검사했다. 공개 게시 주소는 아직 없다.

## 백업과 이전 데이터

- 서버 시작 시와 매시간 유지보수를 수행한다. 생성 후 30일이 지난 검증된 프로젝트 백업만 제거하고, 최소 하루 간격으로 새 백업을 만든다. 서버가 꺼져 있으면 다음 실행 때 처리한다.
- 기존 dump/SQLite 백업 사본은 내용 검사와 해시 등록을 거쳐 동일한 정책으로 관리한다. 알 수 없거나 손상된 파일은 자동 삭제하지 않고 오류로 남긴다. 원본 SQLite와 명시적으로 가져오지 않은 기기 기록은 변경하지 않는다.
- 복원 사본은 기본적으로 서비스할 수 없다. `db:activate`가 이전 DB의 앱 접속을 차단하고 최신 삭제 이력 반영·복원 세션 폐기·명시적 활성화·설정 전환을 수행한다. 퇴역 DB 재활성화는 거부한다.
- 전환 중 강제 종료 후 같은 명령으로 재개하는 테스트를 수행했다. 실제 운영 원본 DB 전환은 실행하지 않았다. [운영 절차](POSTGRES.md)를 따른다.

## 검증과 다음 작업

테스트는 프로젝트의 별도 `speechbridge_test` DB에서 생성한 가상 계정만 사용한다. 13개 사용자 데이터 테이블에 실제 행이 있는지 확인한 뒤 모두 삭제되는지 검사했다. 다른 회원 보존, 잘못된 비밀번호/확인/세션 거부, 로그아웃과 삭제 경합, 삭제 중 로그인 발급 차단, 회원 HTTP 응답, 삭제 전 백업 복원, 예전 SQLite 재가져오기를 확인했다. 전체 서버 테스트98개 통과. 실제 사용자나 시연 계정을 삭제하지 않았다.

클라이언트 검증: Android Host 109개, iOS Simulator 110개 통과. 삭제 응답 유실·재시작, 보안 저장 실패, 일반 만료와 삭제 구분, 다른 계정 보존, 전송 대기 입력 배출 후 삭제, 텍스트/음성/동기화의 삭제 응답 처리를 포함한다. 테스트 개수는 코드 커버리지 수치가 아니다. 서버 전체 98개 통과, 로드된 소스의 line 91.62% / branch 90.19% / function 89.22% (`.runtime/postgres/deletion-devices-coverage.log`).

TDD 체크포인트: `2ae55a4 → 7321889` 다중 기기 삭제 확인, `18c1cb1 → e7cadfa` 계정 복구 상태와 대기함, `9780817 → 0baf9e9` 앱 연결. 마지막 RED는 미구현 `retryDeletionCleanup`/HTTP 클라이언트 주입에서 컴파일 실패했고, 동일 Android 대상과 iOS 대상으로 GREEN 확인했다. 근거 로그는 `.runtime/postgres/deletion-ui-{red,green}.log`다.

직접 앱 검사에서는 삭제 확인창의 비밀번호 없는 확정 비활성화와 취소 후 계정 보존을 확인했다. 시연 계정의 영구 삭제는 실행하지 않았다. 실제 삭제 성공·다른 계정 보존·복원 보호는 별도 테스트 DB의 가상 계정으로 검사했다.

현재 서버 전체 결과는 [배포 직전 검증](PRE_RELEASE.md)이 기준이다. 남은 외부 항목은 공개 HTTPS URL·운영자 정보, 보류한 실기기의 보안 저장소·다중 기기 삭제 검증이다.
